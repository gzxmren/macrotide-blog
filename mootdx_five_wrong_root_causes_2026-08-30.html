排查手记

五版根因，前四版都说得通

一个 A 股数据源挂了 49 个交易日。日志每天都在打警告，信号每天照常推送， 监控全绿。而我给出的前四个根因，每一个当时都严丝合缝。

2026-08-30

先说结论：真相是那个库的默认服务器列表过期了。扫完整个池子 141 台， 21 台完全正常。我花了大半天，绕了四个弯才走到这一步，而这四个弯每一个当时都有证据支撑。

这篇记的不是"怎么修好的"——那部分两行就说完了。记的是我怎么四次确信自己找到了答案， 又怎么四次被推翻。

背景：一个不吵不闹的故障

我有一套 A 股行业 ETF 轮动的影子信号，每个工作日早上 8:30 跑一次。数据源分三层： mootdx（通达信 TCP 协议）打头，失败降级到 AKShare，再降级到 BaoStock。

从 6 月 17 日开始，mootdx 每天失败。降级链正常工作，信号照常算出来、照常推到 Telegram。 日志里每天有十行警告，但日志没人读。

这个状态持续了 49 个交易日。两个半月。系统的输出和一切正常时一模一样， 唯一的差别是那个"主源"从来没供过一次数——备源写在代码里，实际上单腿在跑。

第一版：网络不通

我先跑了个探针，结果看着很干脆：

L1 汇总：TCP 通 8/8　协议层真正响应 0/8
L2 mootdx 客户端：❌ bestip 和默认服务器都 TimeoutError

TCP 全通、协议层零响应。我写下"这个数据源不可访问"。

追问

「mootdx 不是网络层不可访问，是在协议层被屏蔽了」

这句订正看着只是措辞，实际上把问题往下推了一层。"不可访问"是个笼统词， 它把 TCP 和协议糊在一起；一旦说清是"哪一层"，后面的排查方向就完全不同了—— 网络不通该去查路由和防火墙，协议不通该去查协议本身。

第二版：海外 IP 被拒

顺着"协议层"这条线，我找到一个 GitHub 上的 A 股数据工具集，9300 多颗星。 它的文档里有这么一句：

海外 IP 用户：mootdx 走通达信 TCP 7709，海外环境通常全部超时…… 表现为「TCP 可达但返回空 / 被 reset」

和我看到的一字不差。我去查本机出口，是东京的一个云厂 IP。证据链闭合了： 海外 IP → 通达信在应用层拒绝 → TCP 通但协议不响应。

我把这个结论写进了记录。

追问

「我当前通过代理连东京 IP。你能解决多 IP 共存吗，例如访问 mootdx 的时候就用深圳电信的网络 IP， 其他时候都用 tokyo IP」

这个问题顺着我的结论提了个需求，本身没有质疑的意思。但要回答它，我得先搞清楚现在的流量到底怎么走。 一查代理配置，路由规则第 11 条写着 geoip:cn → direct。我做了个对照：

访问国内服务  →  广东深圳，中国电信
访问国外服务  →  东京

分流一直在正常工作。我又把代理的 geoip 数据库解出来（17.6MB，中国段 5806 条）， 逐个核对那些通达信服务器的 IP——全部命中 geoip:cn。

mootdx 的流量从来没走过东京，一直是深圳电信直连。第二版塌了。

我错在哪儿？我测的是"访问 ipinfo.io"的出口，然后拿它推断"访问 mootdx"的出口。 而这台机器恰恰是按目标分流的，两个不同目标的出口本来就不一样。 一个连接的表现，代表不了另一个连接。

第三版：服务端拒绝响应

既然走的是国内直连还失败，那问题只能在服务端了。我又一次觉得自己想通了。

追问

「那么问题根源是服务端修改了 api 接口？因此访问出错？」

这个"为什么"问得很具体，具体到我没法再用笼统词回答。我只好去做字节级抓包—— 手工构造通达信的握手包发过去，看服务器到底回了什么。

119.97.185.59    → 收到 98 字节  b1cb7400 1c02189300000d005200bd00...
124.70.133.119   → 收到 205 字节 b1cb7400 0c02189300000d00bd00bd00...
110.41.147.114   → 收到 98 字节  b1cb7400 1c02189300000d005200bd00...

b1cb7400 是通达信协议的标准响应头。服务器 0.03 秒就正常应答了。

协议层根本没被屏蔽。第三版也塌了——而且塌得比前两版更彻底，因为"被屏蔽"这个说法 （连同我上一轮接受的那句订正）从头就是错的。

第四版：K 线接口被停供

协议通、握手正常，那就往里再拆一层，逐个 API 试：

connect()                  ✅ 0.32s
get_security_count(0 深)    ✅ 24132
get_security_count(1 沪)    ✅ 27842      ← 真实的股票数量
get_security_bars(...)     ❌ None
get_index_bars(...)        ❌ None

连接正常、鉴权正常、股票数量查询返回的是真值，唯独 K 线拿不到。 我又扫了 12 个周期参数、两个市场、个股指数 ETF 三类标的，全是 None。

然后抓 K 线请求的原始字节，发现更精确的东西：

→发 38 字节   0c01086401011c001c002d050100 303030303031 09 ...
←收 16 字节   b1cb7400 ...        ← 协议头正常，能解析
←收  2 字节   2003                ← 数据体，uint16 = 800

我请求 1 根、5 根、100 根、800 根，返回的数据体永远是同一个 2003。 真实数据会随请求变化，固定不变的只能是常量响应。

于是我下了第四个结论：接口和协议都没变，是服务端不再返回 K 线内容了。 这次我甚至觉得自己做得很扎实——毕竟都抓到字节级了。

追问

「那那个 github 项目也应该无法访问 mootdx 的 k 线数据，对不对」

这一问是全程最致命的。

它没有质疑我的证据，而是把我的结论推成了一个可以检验的预测： 如果"服务端停供 K 线"成立，那所有人、所有服务器都该拿不到。这是能验的。

我去扫了完整的服务器池——mootdx 自带 38 台加上底层库的 104 台，去重后 141 台：

可连且 get_security_count 正常：47/141
能取到 K 线：                   21/141

21 台完全正常。第四版当场死亡。

真相：默认列表过期了

把能用和不能用的分开一看，规律很干净：

状态服务器
失效清一色云中转服务器（几个公有云的网段）
正常传统电信主站与券商：上海电信、杭州电信、北京联通、国泰君安、安信

而 mootdx 的默认服务器池，恰好全是前者。所以默认配置必然失败，和网络、和地理位置、 和协议版本都没关系。

我用能用的那几台重测了真正需要的标的：

CSI300 指数   2026-08-28  收 4609.18
ETF 515000   2026-08-28  收 1.279
ETF 512400   2026-08-28  收 1.982

和我同一天接进来的另一个数据源（腾讯财经 HTTP）返回的数字逐位一致。两个独立源交叉验证， 这个数据源从头到尾都是好的。

最毒的一环：验活验了个寂寞

还剩一个问题没解释：这个库有 bestip 机制，启动时会测速选最快的服务器， 而且它不只测 TCP 延迟，还会做一次真实的协议调用来验活。既然会验活，为什么每次都选中一台取不到数的？

因为它验活用的是 get_security_count。

回头看那台坏服务器的表现：get_security_count 返回 27842， 一个完全正确的股票数量；get_security_bars 返回空。

验活必然通过，取数必然为空。这就是 49 个交易日的全部答案。

一个对目标故障没有分辨力的检查，比没有检查更糟——因为它让人以为验过了。

修法很简单，把验活换成真正拉一根 K 线：

def _validate_client(c):
    df = c.bars(symbol="000001", category=4, offset=1)
    return df is not None and not df.empty

加上一份实测可用的服务器列表，逐台试到验活通过为止。建连从原来的 15 秒（还必然失败） 变成 0.45 秒，取数 0.04 秒。

顺带说一句：那个 9300 星的项目文档里，硬编码了 10 台"实测可用"的服务器， 标注的验证时间是 2026 年 6 月。我实测这 10 台，0/10 可用—— 和我自己踩的是同一个坑。所以真正该做对的不是列表，是验活机制：列表总会过期， 而一个正确的验活会在过期时立刻报错降级，不会静默地供空数据。

顺手捡到的一个坑：TUN 下的 connect() 会骗人

排查中途我做过一个对照，本意是想看走不走代理有没有区别：

默认路径（经 TUN）   TCP ✅ 0.00s
绑定物理网卡         TCP ✅ 0.03s

两条都"连上了"，但耗时差了一个数量级。0.03 秒是真实的往返延迟， 0.00 秒是 TUN 设备在本地直接应答了——连接请求还没出机器。

也就是说，在 TUN 模式下 connect() 返回成功，不代表真的连到了远端。 我前面报的那句"TCP 通 8/8"，全是假象。这条对以后任何在代理环境下做网络诊断都适用。

我到底错在哪儿

五个版本，前四个都有证据、都自洽、都能解释我当时看到的现象。但它们全错。

复盘下来，我的毛病是同一个：观察到现象，找到一个能说明它的解释，就停下来宣布这是根因。 从来不主动问"如果这个解释是对的，它还必然意味着什么"。

四次推翻我的，都是外面来的追问，一共四种：

追问方式它逼我做了什么
订正措辞精度
「不是网络层，是协议层」		逼我分层。笼统词恰好掩盖了"哪一层"这个关键信息
基于我的结论提个需求
「那你能做分流吗」		逼我验证结论的可操作后果，一查发现分流早就在做
问"为什么"而不是"是什么"
「为什么协议层回错」		逼我从现象下到机制，才有了字节级抓包
把结论推成预测
「那那个项目也该拿不到吧」		最致命的一招，一验就塌

最后这一招是可以自己对自己用的，而且成本极低。当我第四次宣布"服务端停供 K 线"时， 只要多问一句"那所有服务器都该取不到"，然后扫一遍池子——几分钟的事， 整条错误链就断在那里了。

我没扫。倒不是嫌贵——压根没往"我的样本能代表全体吗"这个方向想过。 测了 10 台就当成了 141 台。

留下来的三个问句

这次之后，我把三句话钉在了"我正要宣布根因"这个时刻：

  • 如果这个解释是对的，它还必然意味着什么？——然后去验那个推论。 不是"它能解释我看到的"，而是"它预测了我还没看的什么"。
  • 已有的记录里，有没有跟它冲突的观测？——第二版塌掉之前， 我自己两个月前写的排查笔记里就白纸黑字记着"出口是国内电信 IP"，直接和"海外 IP"冲突，我没去对。
  • 我的样本是几个？能代表全体吗？——不能就去穷尽。 判断标准是穷尽的成本对比结论错误的代价：这次扫全池几分钟，而错误结论的代价是白白弃用一个可用数据源两个半月。

三问都答完了才算停，这是"穷尽即停"。我原来的模式是"够用即停"——找到一个说得通的就收工。

真正有效的动作也只有三类，都很朴素：分层拆解（TCP、握手、逐个 API，每一层的"正常" 都在切分搜索空间）、穷尽样本（141 台而不是 10 台）、对照实验（绑物理网卡对比默认路径， 一次排除掉代理、路由、出口 IP 全部嫌疑）。

最后留一个也许更值得琢磨的事实：这个故障能藏 49 个交易日，不是因为它隐蔽， 而是因为系统在故障状态下的输出，和正常时完全一样。信号照出、消息照推、 日志照打。降级链设计得很好，好到把主源已经死了这件事完全吸收掉了。

冗余的价值在于备源能顶上。但如果没人验证主源还活着，那所谓的三层降级， 实际上跑的是单腿。
