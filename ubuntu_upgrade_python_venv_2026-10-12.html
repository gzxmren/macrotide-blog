排查手记

升级到 Ubuntu 26.04 之后，Python 虚拟环境的排查和修复记录

系统升级换掉了默认的 Python 版本，每天晚上推送交易信号的程序在导入第一个第三方库时就退出了， 而且没有发出任何报错。这篇记录我和 Claude 当晚从发现问题、找原因、修复，到把整台机器检查一遍的全过程， 也记下了中间做错的几件事。

2026-10-12

我有一套自己搭的量化信号系统，跑在家里一台 Linux 机器上。日常的研究、维护和排查， 是我和 Claude（在终端里用 Claude Code）一起做的。

10 月 12 日傍晚，我把这台机器从 Ubuntu 24.04 升级到 26.04。升级本身很顺利，重启后桌面、网络、 Docker 都正常。我以为事情就结束了。

发现问题

重启后十分钟，我打开 Claude Code 说了一句「我回来了」。按照项目里的约定，Claude 每次开工前会先看一遍 待办和系统状态。它注意到一个细节：信号程序最新一次的输出文件，日期还停在 10 月 9 日。

这个程序每个工作日 19:30 由定时任务启动，算出当天的目标仓位，推送到我的 Telegram。10 月 12 日是周一， 19:30 应该已经跑过了。Claude 去翻日志，最后几行是：

Traceback (most recent call last):
  File "daily_signal.py", line 19, in <module>
    import numpy as np
ModuleNotFoundError: No module named 'numpy'

numpy 是这个程序依赖最深的库，从建这个虚拟环境起就装在里面，从来没动过。19:40 的另一个定时任务 （记录每天的行情状态）也以同样的方式退出了，报的是找不到 yfinance。

更让我在意的是，这次崩溃没有发出任何通知。程序本身有报错推送：出了异常会往 Telegram 发一条「信号脚本出错」。但这段逻辑写在主函数里，而这次程序在文件第 19 行导入 numpy 时就退出了， 主函数根本没有执行到。如果不是当晚恰好打开终端，我要等到第二天发现「昨晚怎么没收到信号」才会知道。

找原因

Claude 先猜是虚拟环境和系统升级有关，然后用下面几条命令去核实：

$ ls -l .venv/bin/python*
python   -> python3
python3  -> /usr/bin/python3
python3.12 -> python3

$ .venv/bin/python -c "import sys; print(sys.version)"
3.14.4

$ ls .venv/lib/
python3.12

$ ls -l /usr/bin/python3
/usr/bin/python3 -> python3.14

四条命令把原因说清楚了：

  • 项目的虚拟环境是今年 5 月用 Python 3.12 建的，所有第三方包都装在 .venv/lib/python3.12/ 下面。
  • 虚拟环境里的 python3 不是一个独立的程序，只是一个指向系统 /usr/bin/python3 的链接。
  • Ubuntu 26.04 把系统默认的 python3 从 3.12 换成了 3.14。
  • 于是虚拟环境实际运行的是 3.14，而 3.14 只会去 lib/python3.14/ 里找包，那个目录不存在。

时间也对得上。升级日志显示，装新软件包是 19:15 到 19:36，19:30 的定时任务正好撞在中间； 上午 8:30 和下午 4:30 的另外两个定时任务在升级之前跑完，结果正常。

还有一个顺带的发现：会话开始时，Claude Code 提示有一个计算工具服务连接失败。这个服务也是从同一个虚拟环境启动的， 原因相同。

先让今晚的信号发出去

美股 22:30 开盘，当晚的信号需要尽快补上。Claude 先确认了一件事：旧版本的 Python 3.12 还在系统里， 没有被升级删掉。所以最快的办法是把虚拟环境的链接改回去：

ln -sfn /usr/bin/python3.12 .venv/bin/python3

改完以后，它先跑了一遍信号程序的测试，701 条全部通过，然后按定时任务的原命令补跑。19:53 信号推送到了 Telegram，内容和前几天的档位一致。行情记录也补跑了。

补完信号，Claude 又查了 3.12 在新系统里的状态：

$ apt list --installed | grep python3.12
python3.12/now 3.12.3-1ubuntu0.17 amd64 [installed,local]

[installed,local] 的意思是：这个包装在本机，但新系统的软件仓库里已经没有它了， 而且它被标记为「自动安装」。下次我执行 apt autoremove 清理不用的包， 它就会被删掉，信号程序会以同样的方式再崩一次。所以改链接只是临时办法。

在 Python 3.14 上重建虚拟环境

我请 Claude 做长期的修法：在 3.14 上重建虚拟环境。我们约定的做法是先另建一个，测试全部通过后再替换， 旧的那个不删，留作回滚。

第一个问题：系统没有建虚拟环境的组件

python3.14 -m venv 可以执行，但新环境里没有 pip，因为 Ubuntu 把这部分拆成了一个单独的包 python3.14-venv，默认没装。Claude 发现我的用户目录里有 uv（一个 Python 包管理工具）， 就改用它来建，不需要 sudo：

uv venv --seed -p /usr/bin/python3.14 .venv314

第二个问题：旧环境本身有依赖冲突

它先把旧环境的包清单导出来，一共 206 个包，然后让 uv 按清单装。uv 拒绝了：

Because mootdx==0.11.7 depends on httpx>=0.25.0,<0.26.0 and you require httpx==0.28.1,
we can conclude that your requirements and mootdx==0.11.7 are incompatible.

也就是说，旧环境里装的 httpx 版本不满足 mootdx 声明的要求，当初大概是先装 mootdx、后来别的包把 httpx 升上去了。这个组合实际用了几个月，没有出过问题。

这时候有两个选择：让 uv 重新求解一套「合规」的版本，或者原样复刻旧环境。Claude 选了后者， 理由是这次的目标是「换 Python 版本，别的都不变」。如果同时换掉一批包的版本，之后出了问题就分不清是哪一边造成的。 它加上 --no-deps，让 uv 不做依赖求解，按清单逐个装。

第三个问题：有一个包装不上

205 个包装上了，只有 coincurve（一个加密签名库）失败：它没有给 3.14 准备编译好的安装包， 现场编译又出错。Claude 查了是谁依赖它：只有 ccxt（加密货币交易所的接口库），而且只在给交易所下单签名时才用到。 我的项目只用 ccxt 取公开行情。它确认缺了这个包，ccxt 仍然能正常导入，就把这一项记成已知缺口，继续往下走。

第四个问题：一条测试在 3.14 上失败

新旧两个环境，Claude 各把 10 组测试跑了一遍。旧环境全过，新环境只有一条失败：

_pickle.PicklingError: Can't pickle local object
  <function test_concurrent_write_does_not_lose_update.<locals>.worker>

原因是 Python 3.14 在 Linux 上改了多进程的默认启动方式：以前是直接复制当前进程（fork）， 现在改成先启动一个服务进程，再由它派生子进程（forkserver）。后一种方式要求交给子进程的函数能被序列化， 而这条测试把函数定义在了测试内部。

Claude 先确认生产代码里没有任何地方用多进程，问题只在测试的写法上。修法是一行：在测试里明确指定用 fork。

改完它又多做了一步。这条测试本来要验证的是「两个程序同时写同一个日志文件，不会互相覆盖掉对方写的内容」， 代码里靠一个文件锁来保证。它在临时副本里把锁去掉，再跑这条测试：

1 passed   (拿掉锁，跑 5 次，5 次都通过)

没有锁，测试照样通过。也就是说，这条测试其实抓不到它要防的问题。在旧的 3.12 环境里试，结果一样， 所以这是测试原本就有的缺陷，和这次升级无关。Claude 没有顺手去改，把它记成了单独的待办。

用真实数据对比，然后替换

测试全过还不够。Claude 用真实行情，把三个每天运行的程序在新旧环境里各跑了一遍「只计算、不推送」的模式， 比较输出。美股和港股两个程序的输出完全一致，A 股那个有一处不同：新环境那次读的是旧环境刚写下的本地缓存， 并没有真正联网取数据。它又单独让新环境直接调用两个 A 股数据接口，确认能联网取到当天的数据，结果和旧环境一致。

替换时还有一个细节。新环境里有 58 个启动脚本，开头写死了 .venv314 这个路径，包括定时任务要用的 activate 脚本。如果只改目录名，定时任务激活环境后会找不到 Python，然后退回到系统的 3.14， 等于又回到出事时的状态。所以改名之后，它把这些脚本里的路径一起改掉，再按定时任务的原命令格式验证了一遍：

mv .venv .venv312          # 旧环境留作回滚
mv .venv314 .venv
# 把 .venv/bin/ 下脚本里写死的 .venv314 改成 .venv
source .venv/bin/activate && python -c "import sys, numpy, pandas; print(sys.version)"
3.14.4

项目里其他代码有没有受影响

我接着问：项目里其他的模块呢？上面跑的测试只覆盖了一部分代码。Claude 把项目里的代码分成三类，分别处理：

代码类型检查方法结果
有测试的（12 组）新旧环境各跑一遍，比较通过数量两边都是 1934 条全过
带自检程序的（4 个估值模型）运行自检，比较输出逐字一致
没有测试的（约 150 个研究脚本）不运行，只用 3.14 编译每个文件，再逐个查它引用的第三方包在新环境里找不找得到262 个文件全部编译通过；新环境没有比旧环境多缺任何包

第三类不直接运行，是因为很多研究脚本一启动就开始跑回测、联网，有的还会推送消息。 这项检查本身能不能发现问题，也有现成的证据：它报出了一个缺失的包（浏览器自动化库）， 只是那个包在旧环境里也没有，用到它的脚本 9 月底就已经失效了。

最后是只在周六运行的几个定时任务，也用不推送的方式试跑。这里我们出了一个错，下一节单独说。

做错的事

试跑覆盖了一个文件

Claude 试跑周报程序之前，打算先备份它会写的文件，但它是凭猜测写的文件名，猜错了。周报程序在不推送的模式下， 仍然会重新生成上一周的周报网页，于是 10 月 5 日那一周的周报网页被覆盖了，没有备份。

这份网页是从交易记录和行情现算出来的，上一周的数据都已经确定。Claude 隔几分钟连跑两次，生成的内容逐字相同， 所以重新生成的这份大概率和原件一样。但原件已经没有了，这一点没法证明。

之后的几个任务，它改成先把相关目录整体复制一份（588MB），跑完再逐个文件比对、恢复。 这一步又发现美股选股程序在不推送的模式下也会重写一个记录文件，已经从备份里恢复。

我

先弄清楚一个程序会写哪些文件，再去跑它。凭文件名去猜，猜错的代价就是丢数据。

报错了两个数

后面检查整台机器时，Claude 报告「其他项目里有 15 个虚拟环境坏了」。等我决定修、它把清单逐个列出来时， 发现实际是 14 个，随后更正了。

另一个是测试总数。它当晚告诉我 12 组测试共 2134 条，直到写这篇文章、逐条核对数字时才发现， 各组相加是 1934 条，多算了 200。每一组在两个环境里的通过数量都是对的，错在最后那一步加法。

这两个数都不影响结论，但如果我拿着错的数去核对，就会花时间去找不存在的东西。

把整台机器检查一遍

项目修好以后，我让 Claude 检查机器上的其他东西：别的项目、Claude Code 本身、插件、技能和 MCP 服务 （Claude Code 用来接外部工具的服务）。它按四块来查，每一块都尽量实际启动，而不是只看配置文件。

没受影响的

  • Claude Code 本体：自带的诊断命令 claude doctor 报告没有问题。
  • Node、Bun、Git、Docker 等程序，以及 Node 全局包、Bun 和插件目录里的 552 个编译好的库文件，用 ldd 逐个检查依赖的系统库。 报告缺库的有不少，但都是给别的平台准备的备用文件（32 位、musl、OpenBSD），或者是 NVIDIA 显卡加速版本， 这台 AMD 机器本来就不会加载。排除这些之后，缺库数是 0。
  • 本地运行的三个 MCP 服务，都实际启动并完成了握手。其他远程服务跑在云端，与本机系统无关。

受影响的，有三处

三处的原因和前面一样，都是默认的 python3 变了：

  1. 一个 Telegram 消息转发服务停了。它是系统服务，直接用 /usr/bin/python3 启动， 依赖的库装在我用户目录下 3.12 专用的包目录里。升级后它连续启动失败，系统放弃了重试。在这之前，它已经连续运行了 13 天。
  2. 用户目录里有 585 个包，3.14 看不到。这是以前用 pip install --user 装的， 只对 3.12 有效。受影响最明显的是一个金融分析插件里的 Excel 模型校验脚本，它找不到读 Excel 用的 openpyxl。
  3. 其他项目里还有 14 个虚拟环境，坏法和上面一样。它们没有挂在定时任务或后台服务上， 所以要等我打开那个项目时才会发现。

还查到两个以前就坏了的东西：一个网络流量告警服务，日志显示 9 月以来每次开机都是连启 5 次就放弃； 另一个服务的连接报错，升级前的日志里也有。判断它们和升级无关，靠的是对比升级前那次开机的日志， 而不是看到报错就算到升级头上。

怎么修

这三处，我选的都是「先指回 3.12」的办法。代价最小，也能完整恢复到升级前的状态，以后哪个项目还在积极开发， 再单独在 3.14 上重建：

问题做法撤销方法
3.12 可能被自动清理掉sudo apt-mark manual python3.12 …，再模拟一次 apt autoremove，确认不会删它改回自动标记
Telegram 转发服务不改原来的服务文件，另加一个覆盖配置，只把启动命令换成 /usr/bin/python3.12删掉这个覆盖配置
用户目录的 585 个包在 ~/.local/bin/ 放一个指向 3.12 的 python3，让终端、Claude Code 和技能脚本里的 python3 回到升级前的状态删掉这个链接
14 个项目的虚拟环境每个都把 bin/python3 改指向 3.12，改前先把原来的指向记到一个文件里按记录改回去

第三条只影响我自己的命令路径。系统自带的工具写死了 /usr/bin/python3， 定时任务的命令路径里也没有我的用户目录，所以这两类都不受影响。

每一条修完都实际验证过：转发服务重启后在正常工作，没有再重启；Excel 校验脚本用一份真实的估值模型去跑， 3.14 下报「没装 openpyxl」，修完后检查了 717 个公式，没有错误；14 个虚拟环境逐个确认版本是 3.12， 并且把每个环境里装的包实际导入一遍，一共 816 个，没有失败的。最后把全机的虚拟环境重新扫了一遍， 这次多扫了两层目录，找到 27 个，全部正常。

回头看

这次的原因只有一个：虚拟环境里的 python3 只是一个指向系统 Python 的链接， 系统一换版本，它就跟着换了，而包还留在旧版本的目录里。这台机器上用 uv 自带的 Python 建的环境， 以及链接指向带版本号的 python3.12 的环境，这次都没受影响。

信号程序崩了，却没有发出通知。报错推送写在主函数里，就只能管到主函数里的错误。 程序在更早的地方退出时，这层保护等于没有。这个缺口我还没补，补法大概是在定时任务这一层，而不是在程序内部。

那条并发测试从 9 月初加进项目，一直是通过的。 如果不是这次因为 3.14 改了启动方式、它变红了一次，我们不会去试「拿掉锁会怎样」，也就不会知道它什么都没验证。

另外两个看起来像升级引起的服务故障，一对比上一次开机的日志，就知道它们早就存在了。判断一个问题是不是升级造成的， 要拿升级前的记录来对。

写于 2026-10-12。文中的命令输出、数字和时间都来自当晚的终端记录和系统日志；路径做了简化。

环境：Ubuntu 24.04 → 26.04，系统 Python 3.12.3 → 3.14.4，Claude Code 2.1.296。
