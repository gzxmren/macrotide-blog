人机协作排查手记

AI 给了我五版根因，前四版都说得通

它能在三分钟内扫完 141 台服务器、手工构造二进制协议包抓字节、解开一个 17.6MB 的数据库文件——却想不到应该去扫。这是一次真实排查的完整记录，包括我们各自 做对了什么、错在哪里。

2026-08-30

我有一套自建的量化信号系统，日常研究和排查是我和 Claude 一起做的。 这次的事情是：一个 A 股数据源挂了 49 个交易日没人发现，我们花了大半天把它挖出来。

过程中它给了五个根因，前四个全错，而每一个当时都有证据、都自洽、都能解释我们看到的现象。 最后的真相简单得可笑——那个库的默认服务器列表过期了。

值得写下来的不是"怎么修好的"，而是四次错误分别是怎么被推翻的， 以及从中能看出 AI 在这类工作里到底强在哪、弱在哪。

背景：一个不吵不闹的故障

系统里有一套 A 股行业 ETF 轮动的影子信号，每个工作日早上 8:30 跑。 数据源分三层：mootdx（通达信 TCP 协议）打头，失败降级到 AKShare，再降级到 BaoStock。

从 6 月 17 日开始，mootdx 每天失败。降级链正常工作，信号照常算出来、照常推到 Telegram。 日志里每天有十行警告，但日志没人读。

这个状态持续了 49 个交易日。系统的输出和一切正常时一模一样， 唯一的差别是那个"主源"从来没供过一次数——三层降级写在代码里，实际上一直在单腿跑。

第一版：网络不通

它先跑了个探针，结果看着很干脆：

L1 汇总：TCP 通 8/8　协议层真正响应 0/8
L2 mootdx 客户端：❌ bestip 和默认服务器都 TimeoutError

TCP 全通、协议层零响应。它的结论是"这个数据源不可访问"。

作者

mootdx 不是网络层不可访问，是在协议层被屏蔽了。

这句听着像抠字眼，实际上把问题往下推了一层。"不可访问"是个笼统词，把 TCP 和协议糊在了一起； 一旦说清是哪一层，排查方向就完全不同——网络不通该查路由和防火墙，协议不通该查协议本身。

第二版：海外 IP 被拒

顺着"协议层"这条线，它找到一个 GitHub 上的 A 股数据工具集，9300 多颗星，文档里有这么一句：

海外 IP 用户：mootdx 走通达信 TCP 7709，海外环境通常全部超时…… 表现为「TCP 可达但返回空 / 被 reset」

和我们看到的一字不差。它去查本机出口，是东京的一个云厂 IP。证据链闭合了： 海外 IP → 通达信在应用层拒绝 → TCP 通但协议不响应。它把这个结论写进了记录。

我当时没觉得哪里不对，顺着这个结论提了个需求：

作者

我当前通过代理连东京 IP。你能解决多 IP 共存吗，例如访问 mootdx 的时候就用深圳电信的网络 IP， 其他时候都用 tokyo IP。

这个问题本身不带怀疑，但要回答它，它得先搞清楚现在的流量到底怎么走。一查代理配置， 路由规则第 11 条写着 geoip:cn → direct。做个对照：

访问国内服务  →  广东深圳，中国电信
访问国外服务  →  东京

分流一直在正常工作。它又把代理的 geoip 数据库解出来（17.6MB 的 protobuf，中国段 5806 条）， 逐个核对那些通达信服务器的 IP——全部命中 geoip:cn。

mootdx 的流量从来没走过东京，一直是深圳电信直连。第二版不成立。

错在哪儿？它测的是"访问 ipinfo.io"的出口，然后拿这个去推断"访问 mootdx"的出口。 而这台机器恰恰是按目标分流的，两个不同目标的出口本来就不一样。 一个连接的表现，代表不了另一个连接。

第三版：服务端拒绝响应

既然走的是国内直连还失败，那问题只能在服务端了。它又一次觉得想通了。

作者

那么问题根源是服务端修改了 api 接口？因此访问出错？

这个"为什么"问得具体，具体到没法再用笼统词回答。它只好去做字节级抓包—— 手工构造通达信的握手包发过去，看服务器到底回什么。

119.97.185.59    → 收到 98 字节  b1cb7400 1c02189300000d005200bd00...
124.70.133.119   → 收到 205 字节 b1cb7400 0c02189300000d00bd00bd00...
110.41.147.114   → 收到 98 字节  b1cb7400 1c02189300000d005200bd00...

b1cb7400 是通达信协议的标准响应头。服务器 0.03 秒就正常应答了。

协议层根本没被屏蔽。第三版同样不成立——而且比前两版错得更远，因为"被屏蔽"这个说法 （包括我上一轮给它的那句订正）从头就是错的。

第四版：K 线接口被停供

协议通、握手正常，那就往里再拆一层，逐个 API 试：

connect()                  ✅ 0.32s
get_security_count(0 深)    ✅ 24132
get_security_count(1 沪)    ✅ 27842      ← 真实的股票数量
get_security_bars(...)     ❌ None
get_index_bars(...)        ❌ None

连接正常、鉴权正常、股票数量返回的是真值，唯独 K 线拿不到。 它又扫了 12 个周期参数、两个市场、个股指数 ETF 三类标的，全是 None。

然后抓 K 线请求的原始字节：

→发 38 字节   0c01086401011c001c002d050100 303030303031 09 ...
←收 16 字节   b1cb7400 ...        ← 协议头正常，能解析
←收  2 字节   2003                ← 数据体，uint16 = 800

请求 1 根、5 根、100 根、800 根，返回的数据体永远是同一个 2003。 真实数据会随请求变化，固定不变的只能是常量响应。

于是第四个结论：接口和协议都没变，是服务端不再返回 K 线内容了。这次连字节都抓到了， 看着相当扎实。

作者

那那个 github 项目也应该无法访问 mootdx 的 k 线数据，对不对？

这一问是全程最要紧的。

我没有质疑它的任何一条证据，只是把它的结论推成了一个可以检验的预测： 如果"服务端停供 K 线"成立，那所有人、所有服务器都该拿不到。这是能验的。

它去扫了完整的服务器池——mootdx 自带 38 台加上底层库的 104 台，去重后 141 台：

可连且 get_security_count 正常：47/141
能取到 K 线：                   21/141

21 台完全正常。第四版就此作废。

真相：默认列表过期了

把能用和不能用的分开，规律很干净：失效的清一色是云中转服务器（几个公有云的网段）， 正常的是传统电信主站和券商服务器——上海电信、杭州电信、北京联通、国泰君安、安信。

而 mootdx 的默认服务器池，恰好全是前者。所以默认配置必然失败，和网络、地理位置、 协议版本都没关系。

用能用的那几台重测真正需要的标的：

CSI300 指数   2026-08-28  收 4609.18
ETF 515000   2026-08-28  收 1.279
ETF 512400   2026-08-28  收 1.982

和同一天接进来的另一个数据源（腾讯财经 HTTP）返回的数字逐位一致。 两个独立源交叉验证，这个数据源从头到尾都是好的。

回头看这条定位路径

起点是「mootdx 的服务器 IP 访问不了」，终点是「云厂商的中转服务器整体失效， 而传统电信主站一直好着」。这两句话之间隔着四轮对话。

把它串起来看，会发现每一轮都不是换了个新猜测，而是把搜索空间切掉了一整块：

起点  mootdx 的服务器 IP 访问不了          ← 笼统，混着好几种机制

 ├ 对话①  不是网络层，是协议层
 │         → 逼出分层           排除「网络不通」      实测 TCP 通 8/8
 │
 ├ 对话②  那你能做分流吗
 │         → 逼出查真实路由      排除「海外 IP 被拒」  流量本就走深圳直连
 │
 ├ 对话③  为什么协议层会回错
 │         → 逼出字节级抓包      排除「协议被屏蔽」    服务器 0.03s 正常应答
 │
 ├ 对话④  那那个项目也该拿不到吧
 │         → 逼出扫描全池        排除「服务端停供」    141 台里 21 台正常
 │
终点  云中转服务器失效，传统主站正常          ← 具体到可以直接修

四次排除掉的东西，范围一次比一次小：从「整个网络」到「地理位置」到「整个协议」 到「整个服务端」，最后落到「服务器名单里的某一类」。

而每一轮的触发点都是同一件事——上一个结论被推成了一个可以检验的说法， 然后去检验它。第一轮检验的是"哪一层不通"，第二轮是"流量到底走哪条路"， 第三轮是"服务器到底回了什么字节"，第四轮是"是不是所有服务器都这样"。

回头看，最省事的其实是第四轮那个问法：它不需要任何新知识，只是把 "服务端停供 K 线"这句话顺着往下说一句——那所有服务器都该取不到吧？ 然后花三分钟扫一遍。如果这个动作提前到第一轮做，中间那三个弯根本不会出现。

最毒的一环：验活验了个寂寞

还剩一个问题：这个库有 bestip 机制，启动时测速选最快的服务器， 而且它不只测 TCP 延迟，还会做一次真实的协议调用来验活。既然会验活， 为什么每次都选中一台取不到数的？

因为它验活用的是 get_security_count。

回头看那台坏服务器：get_security_count 返回 27842， 一个完全正确的股票数量；get_security_bars 返回空。

验活必然通过，取数必然为空。49 个交易日的全部答案就在这里。

一个对目标故障没有分辨力的检查，比没有检查更糟——因为它让人以为验过了。

修法很简单，把验活换成真正拉一根 K 线，再配一份实测可用的服务器列表， 逐台试到验活通过为止。建连从原来的 15 秒（还必然失败）变成 0.45 秒，取数 0.04 秒。

顺带一提：那个 9300 星的项目文档里硬编码了 10 台"实测可用"的服务器，标注的验证时间是 2026 年 6 月。我们实测这 10 台，0/10 可用，和我们踩的是同一个坑。 所以真正该做对的不是那份列表，是验活机制——列表总会过期，而一个正确的验活会在它过期时 立刻报错降级，不会静默地供空数据。

AI 在这次排查里做对了什么

上面全是它的错，容易给人一种"AI 不靠谱"的印象。但如果没有它，这个故障我大概率还挂在那里。 把它实际干的活列出来：

三分钟扫完 141 台服务器

并发探测整个服务器池，每台都做「TCP 握手 + 真实取数」两级验证， 最后给出可用清单和失效规律。这件事我手工做要一下午，而且做到一半就会开始偷懒抽样—— 而抽样恰恰是错误的来源。

手工构造二进制协议包

为了搞清楚"服务器到底回了什么"，它直接按通达信协议拼出握手包发过去， 再 hook 掉底层 socket 把收发字节全打出来。这是能区分"没回"和"回了但解析不了"的唯一办法， 而这两种情况的修复路径完全不同。

解开 17.6MB 的 protobuf 数据库

为了确认那些服务器 IP 到底算不算"国内"，它手写了一个 protobuf 解析器把代理的 geoip 数据库拆开，逐条比对 5806 个网段。没有现成工具，它就自己写一个。

把每一步都变成可复跑的证据

整个过程没有一句"我觉得"。每个结论下面都挂着一段能重跑的代码和一份原始输出。 所以推翻它也很快——数据摆在那里，不需要争论。

修完之后自己写测试并验证护栏有效

修复不只是改代码。它补了针对性的测试，然后故意把代码改坏，确认测试真的会红，再改回来确认变绿。 这一步很多人（包括我）都会省掉，而省掉之后你并不知道那个测试有没有在做事。

它错在哪里：一个很一致的失败模式

四个错误版本，形状是同一个：观察到现象，找到一个能说明它的解释，就停下来宣布这是根因。

它从来不主动问"如果这个解释是对的，它还必然意味着什么"。用它自己后来的话说， 它的默认模式是"够用即停"——找到一个说得通的就收工，而不是"穷尽即停"。

具体到这次，三个动作它一个都没自己做：

  • 没把解释推成预测再去验。第四版宣布"服务端停供"时， 只要多问一句"那所有服务器都该取不到"，然后扫一遍池子——几分钟的事，整条错误链就断在那里。
  • 没去对已有记录里冲突的观测。第二版说"海外 IP 导致"时， 它自己两个月前写的排查笔记里就白纸黑字记着"真实出口是国内电信 IP"，直接冲突，它没去翻。
  • 拿单点外推全体。测了 10 台就当成了 141 台； 拿一个连接的出口就推断另一个连接的出口。

注意最后一条的性质：它有能力三分钟扫完 141 台——它只是没想到要扫。

所以分工在哪儿

这次之后我对人机协作的理解具体了很多：

AI 极擅长「验证」，但不擅长「决定该验证什么」。

它能在三分钟内穷尽一个我根本做不到的搜索空间，能构造二进制包、能手写解析器、 能把每个断言都变成可复跑的代码。这些是实打实的能力，不是噱头。

但"该往哪看"这件事，四次都是我给的。而我给的四句话，回头看是四种不同的招式：

我说的它逼出了什么
订正措辞精度
「不是网络层，是协议层」		 逼它分层。笼统词恰好掩盖了"哪一层"这个关键信息
基于它的结论提个需求
「那你能做分流吗」		 逼它验证结论的可操作后果，一查发现分流早就在做
问"为什么"而不是"是什么"
「为什么协议层回错」		 逼它从现象下到机制，才有了字节级抓包
把结论推成预测
「那那个项目也该拿不到吧」		 最有效的一招，一验就见分晓

这四招都不需要我懂通达信协议。第四招尤其便宜——我只是把它的话顺着往下说了一句， 它自己就去把自己证伪了。

如果你也在用 AI 做这类工作

几条我觉得可以直接用的：

别接受第一个说得通的答案

"说得通"的门槛太低了。四个错误版本每一个都说得通，而且证据一次比一次扎实—— 第四版都抓到字节级了，还是错的。问一句"如果它是对的，还必然意味着什么"， 成本几乎为零。

要求它给可复跑的证据，而不是结论

这次能快速推翻四个版本，靠的是每个结论都挂着代码和原始输出。 如果它只给"我认为是海外 IP 的问题"，那我除了信或不信没有别的选择。

盯住"样本几个"

它报"TCP 通 8/8"的时候，我该问的是"一共几台"。8 台和 141 台之间隔着整个结论。 凡是看到分子分母，先确认分母是全体还是抽样。

笼统词是信号

"不可访问"、"被屏蔽"、"有实质影响"——这类词出现的时候，往下追一层通常就有东西。 它们能同时兼容好几种互斥的机制，所以听起来永远是对的。

它反而不容易犯的错

公平地说，有几类错它基本不犯：算错数、记错自己十步之前说过什么、 懒得把 141 台都跑一遍、嫌麻烦跳过验证。人在长时间排查里这几样全会犯。 所以分工挺清楚的——判断方向归我，密集验证归它。

最后：这个故障为什么能藏 49 天

不是因为它隐蔽。是因为系统在故障状态下的输出，和正常时完全一样。 信号照出、消息照推、日志照打。降级链设计得很好，好到把主源已经死了这件事完全吸收掉了。

冗余的价值在于备源能顶上。但如果没人验证主源还活着，那所谓的三层降级， 实际上一直在单腿跑。

而那个本该发现问题的验活机制，因为用了一个没有分辨力的检查， 49 个交易日里每一天都在报"一切正常"。
